# 07 — Key Vault and secret hygiene

**Time:** 2 hours · **Cost:** ~₹0 (Key Vault is ~₹0.025 per 10,000 operations)
**Prerequisite:** chapters 04–06 complete

The counter-intuitive goal of this chapter: **put as little as possible in Key
Vault.** A secret manager is a place to store secrets safely. Not needing a
secret at all is strictly better.

---

## 1. The hierarchy of secret handling

Work down this list. Only reach a lower rung when the one above is impossible.

| Rung | Approach | Example in this project |
|---|---|---|
| **1. No secret exists** | federated identity / managed identity | PostgreSQL, ACR, Key Vault itself, Service Bus, Cosmos, the Azure DevOps service connection |
| **2. Secret exists but is never handled by a human** | Terraform generates it, writes it straight to Key Vault, nobody ever reads it | the bootstrap DB admin password |
| **3. Secret in Key Vault, delivered by CSI driver as a file** | not in etcd, auto-rotated | third-party API keys |
| **4. Secret in Key Vault, synced to a Kubernetes Secret** | now in etcd — accept only when an env var is unavoidable | App Insights connection string |
| **5. Secret in a pipeline variable group** | masked in logs, but still a stored secret | nothing, in this project |
| **6. Secret in a config file or env var in git** | never | — |

**Count what we actually store:** two secrets, both generated by Terraform and
never seen by a person. Everything else is rung 1.

> **The line that lands in an interview:** *"The question I ask first is not
> 'where should this secret live', it is 'why does this secret exist'. Most of
> them turn out to be avoidable with managed identity, and a secret that does
> not exist cannot leak, expire, or be screenshotted into a ticket."*

## 2. The Key Vault configuration

Read [`infra/terraform/modules/keyvault/main.tf`](../infra/terraform/modules/keyvault/main.tf).

| Setting | Our value | Why |
|---|---|---|
| `rbac_authorization_enabled` | `true` | Entra RBAC, not legacy access policies |
| `purge_protection_enabled` | `false` dev / `true` prod | prod: a deleted secret cannot be permanently destroyed inside the retention window |
| `soft_delete_retention_days` | 7 dev / 90 prod | recovery window for an accidental delete |
| `public_network_access_enabled` | `true` dev (IP-restricted) / `false` prod | prod reaches it only via private endpoint |
| `network_acls.default_action` | `Deny` when private | explicit default-deny |
| diagnostic `AuditEvent` | → Log Analytics | **every secret read, by whom** |

### RBAC mode vs access policies — know the difference

| | **RBAC** (we use this) | Access policies (legacy) |
|---|---|---|
| Model | Azure role assignments | a per-vault ACL list |
| Scope granularity | vault, **or individual secret** | whole vault only |
| Works with PIM | yes | no |
| Deny assignments | yes | no |
| Visible in `az role assignment list` | yes | no — easy to miss in a review |
| Max entries | no practical limit | 1,024 |

The deciding argument: with access policies, "read one secret" and "read every
secret in the vault" are the same permission. With RBAC you can scope
`Key Vault Secrets User` to a single secret. And access-policy grants are
invisible to a normal RBAC audit, which is how over-privileged access survives
reviews.

### The roles, and the one people get wrong

| Role | Can | Our use |
|---|---|---|
| Key Vault Secrets User | **read** secret values | the application identities |
| Key Vault Secrets Officer | read, **write, delete** | the pipeline, for seeding |
| Key Vault Reader | list secret *metadata*, **not values** | the security group |
| Key Vault Administrator | everything incl. RBAC | nobody standing; break-glass only |

**`Contributor` on the vault does NOT let you read a secret.** Control plane
and data plane are separate. A Contributor can delete the entire vault but not
read one secret out of it — which surprises people and is a nice detail to
mention.

```bash
cd infra/terraform/envs/dev
KV_NAME=$(terraform output -raw key_vault_name)
KV_ID=$(az keyvault show -n "$KV_NAME" --query id -o tsv)

az role assignment list --scope "$KV_ID" \
  --query '[].{principal:principalName, type:principalType, role:roleDefinitionName}' -o table

az keyvault secret list --vault-name "$KV_NAME" \
  --query '[].{name:name, enabled:attributes.enabled, expires:attributes.expires}' -o table
```

## 3. The CSI driver — secrets as files, not environment variables

### Why files beat environment variables

| | Environment variable | CSI volume file |
|---|---|---|
| Visible in `kubectl describe pod` | often yes | no |
| In etcd | yes (via a K8s Secret) | **no** |
| Visible to any process via `/proc/<pid>/environ` | yes | no |
| Leaks into crash dumps and error reports | commonly | rarely |
| Updates without a pod restart | no | **yes, with rotation enabled** |
| Child processes inherit it | yes | no |

That last-but-one row is the strongest argument: with `secret_rotation_enabled`
and a 2-minute interval, rotating a secret in Key Vault updates the file in
every mounted pod **without a restart**. With env vars you must redeploy.

### Enable it

```bash
# Seed a secret to read
az keyvault secret set --vault-name "$KV_NAME" \
  --name "erp-appinsights-connection-string" \
  --value "$(terraform output -raw app_insights_connection_string)" \
  --content-type "appinsights" \
  --only-show-errors -o none

# Turn on the Key Vault integration in the chart
TENANT=$(az account show --query tenantId -o tsv)
helm upgrade erp k8s/helm/erp -n erp -f k8s/helm/erp/values-dev.yaml --reuse-values \
  --set config.keyVault.enabled=true \
  --set config.keyVault.name="$KV_NAME" \
  --set config.keyVault.tenantId="$TENANT" \
  --atomic --wait
```

### Verify

```bash
kubectl -n erp get secretproviderclass
kubectl -n erp describe secretproviderclass erp-keyvault

# The mounted files
kubectl -n erp exec deploy/erp-api -- ls -la /mnt/secrets/

# Read one (redacted so you do not paste a secret into a terminal log)
kubectl -n erp exec deploy/erp-api -- sh -c \
  'head -c 25 /mnt/secrets/appinsights-connection-string; echo "...[truncated]"'

# The synced Kubernetes Secret (only the one we deliberately sync)
kubectl -n erp get secret erp-appinsights -o jsonpath='{.data}' | jq 'keys'
```

### The three-way gotcha

For the CSI driver to work, **all three** must line up:

1. the `SecretProviderClass` `clientID` is the managed identity's **client id**
2. that identity has `Key Vault Secrets User` on the vault
3. the pod has the workload identity **label** and the SA has the
   **annotation** (chapter 04)

Miss any one and the pod stays in `ContainerCreating` with a
`FailedMount` event. Debug with:

```bash
kubectl -n erp describe pod -l app.kubernetes.io/component=api | grep -A10 Events
kubectl -n kube-system logs -l app=secrets-store-csi-driver --tail=50
kubectl -n kube-system logs -l app=secrets-store-provider-azure --tail=50
```

That last log line is where the real error is. The pod event just says
"failed to mount"; the provider log says *why* — usually a 403 from Key Vault
or an identity mismatch.

### `secretObjects` — the trade-off to state out loud

```yaml
secretObjects:
  - secretName: erp-appinsights
    data:
      - objectName: appinsights-connection-string
        key: appinsights-connection-string
```

This syncs the file into a Kubernetes Secret so it can be an env var. **That
puts the value in etcd.** We do it for exactly one thing — the App Insights
connection string, because the OpenTelemetry SDK wants an env var — and
nothing else.

> *"I sync only what genuinely must be an environment variable. The file mount
> alone keeps the value out of etcd entirely, and etcd is a shared blast
> radius: anyone with cluster-wide secret read, or an etcd backup, has every
> synced secret."*

## 4. Rotation — demonstrate it

```bash
# 1. What is in the pod right now?
kubectl -n erp exec deploy/erp-api -- \
  md5sum /mnt/secrets/appinsights-connection-string

# 2. Change the secret in Key Vault
az keyvault secret set --vault-name "$KV_NAME" \
  --name "erp-appinsights-connection-string" \
  --value "InstrumentationKey=11111111-1111-1111-1111-111111111111;IngestionEndpoint=https://example/" \
  -o none

# 3. Wait for the rotation interval (we set 2m) and check again
sleep 150
kubectl -n erp exec deploy/erp-api -- \
  md5sum /mnt/secrets/appinsights-connection-string
```

The hash changes **with no pod restart**. Put the real value back:

```bash
az keyvault secret set --vault-name "$KV_NAME" \
  --name "erp-appinsights-connection-string" \
  --value "$(cd infra/terraform/envs/dev && terraform output -raw app_insights_connection_string)" \
  -o none
```

### The honest caveat

The *file* updates. Whether the **application** picks up the new value depends
entirely on the application — if it read the file once at startup and cached
it, rotation achieved nothing. Rotation is an application-design problem as
much as an infrastructure one, and saying so unprompted is a mark of someone
who has actually done it.

For the synced Kubernetes Secret, the CSI driver updates the Secret object but
a pod consuming it as an **env var still needs a restart**, because env vars
are fixed at process start. That asymmetry is the practical reason to prefer
files.

## 5. Secret versioning and expiry

```bash
# Every version of a secret
az keyvault secret list-versions --vault-name "$KV_NAME" \
  --name "erp-appinsights-connection-string" \
  --query '[].{version:name, created:attributes.created, enabled:attributes.enabled}' -o table

# Set an expiry - this is what makes rotation auditable
az keyvault secret set-attributes --vault-name "$KV_NAME" \
  --name "erp-db-admin-password" \
  --expires "$(date -u -d '+90 days' +%Y-%m-%dT%H:%M:%SZ)"

# Find anything expiring in the next 30 days
CUTOFF=$(date -u -d '+30 days' +%Y-%m-%dT%H:%M:%SZ)
az keyvault secret list --vault-name "$KV_NAME" \
  --query "[?attributes.expires != null && attributes.expires < '$CUTOFF'].{name:name, expires:attributes.expires}" \
  -o table
```

**Always set an expiry**, even on a secret you intend to keep. An expiry date
turns "we should rotate that sometime" into a dated obligation you can alert
on. Chapter 11 adds the alert.

## 6. Auditing — who read what

This is the question an auditor asks and most teams cannot answer.

```bash
LAW_GUID=$(az monitor log-analytics workspace show \
  --ids "$(cd infra/terraform/envs/dev && terraform output -raw log_analytics_workspace_id)" \
  --query customerId -o tsv)

az monitor log-analytics query --workspace "$LAW_GUID" --analytics-query '
  AzureDiagnostics
  | where ResourceProvider == "MICROSOFT.KEYVAULT"
  | where Category == "AuditEvent"
  | extend SecretName = tostring(split(id_s, "/")[-2])
  | project TimeGenerated, OperationName, SecretName,
            Caller = identity_claim_upn_s,
            AppId  = identity_claim_appid_g,
            Result = ResultType,
            CallerIP = CallerIPAddress
  | order by TimeGenerated desc
  | take 30' -o table
```

Two queries worth keeping — see [`cheatsheets/kql.md`](cheatsheets/kql.md):

```kql
// Who read secrets they have never read before? (anomaly hunting)
AzureDiagnostics
| where ResourceProvider == "MICROSOFT.KEYVAULT" and OperationName == "SecretGet"
| summarize FirstSeen = min(TimeGenerated), Reads = count()
    by Caller = coalesce(identity_claim_upn_s, identity_claim_appid_g),
       Secret = tostring(split(id_s, "/")[-2])
| where FirstSeen > ago(24h)

// Failed access attempts - either a misconfiguration or someone probing
AzureDiagnostics
| where ResourceProvider == "MICROSOFT.KEYVAULT" and ResultType != "Success"
| summarize Failures = count() by OperationName, ResultType,
    Caller = coalesce(identity_claim_upn_s, identity_claim_appid_g)
| order by Failures desc
```

## 7. Secret scanning — stopping them getting in

Covered fully in chapter 10 §3. The config lives in
[`security/secrets/gitleaks.toml`](../security/secrets/gitleaks.toml) with
custom rules for Azure storage connection strings, Entra client secrets, SAS
tokens, PostgreSQL URIs with inline passwords and embedded kubeconfig certs.

Run it now:

```bash
gitleaks dir . --config security/secrets/gitleaks.toml --redact --verbose
```

### The critical point about remediation

**Deleting a secret in a new commit does not remove it from the repository.**
It is still in history, still in every clone, still reachable by SHA from any
fork.

The correct response, in this order:

1. **Rotate the credential immediately.** It is compromised. This is step one,
   not step three.
2. Remove it from history — `git filter-repo --invert-paths --path <file>`,
   or BFG. Then force-push and have everyone re-clone.
3. Only then worry about why the gate did not catch it.

> *"The moment a secret reaches a repository it is compromised, so the first
> action is always rotation, not cleanup. Scrubbing history is damage
> limitation. That is also why the secret-scanning gate is a hard fail rather
> than a warning — a warning gets ignored, and then you are rotating a
> production credential at 11 p.m."*

## 8. Break it on purpose

**Exercise A — the wrong Key Vault role**

```bash
KV_NAME=$(cd infra/terraform/envs/dev && terraform output -raw key_vault_name)
KV_ID=$(az keyvault show -n "$KV_NAME" --query id -o tsv)
PLATFORM_RG=$(cd infra/terraform/envs/dev && terraform output -json resource_groups | jq -r .platform)
API_PRINCIPAL=$(az identity show -n id-erp-api-dev -g "$PLATFORM_RG" --query principalId -o tsv)

# Remove the data-plane role, but leave everything else intact
az role assignment delete --assignee-object-id "$API_PRINCIPAL" \
  --role "Key Vault Secrets User" --scope "$KV_ID"

kubectl -n erp rollout restart deploy/erp-api
kubectl -n erp get pods    # stuck in ContainerCreating
kubectl -n erp describe pod -l app.kubernetes.io/component=api | grep -A8 Events
kubectl -n kube-system logs -l app=secrets-store-provider-azure --tail=20
```

You get a **403 Forbidden** from Key Vault in the *provider* log, and a
generic `FailedMount` in the pod events. That gap — generic event, specific
provider log — is the thing to remember.

Restore: `cd infra/terraform/envs/dev && terraform apply -auto-approve`

**Exercise B — Contributor cannot read a secret**

```bash
# Prove the control-plane / data-plane split
az role assignment create --assignee-object-id "$API_PRINCIPAL" \
  --assignee-principal-type ServicePrincipal \
  --role "Contributor" --scope "$KV_ID"

# Contributor can see the vault's configuration...
az keyvault show -n "$KV_NAME" --query name -o tsv

# ...and could delete the whole vault, but still cannot read a secret value.
# Only "Key Vault Secrets User" or above grants that.

az role assignment delete --assignee-object-id "$API_PRINCIPAL" \
  --role "Contributor" --scope "$KV_ID"
```

**Exercise C — soft delete and recovery**

```bash
az keyvault secret set --vault-name "$KV_NAME" --name "test-delete-me" --value "temp" -o none

az keyvault secret delete --vault-name "$KV_NAME" --name "test-delete-me"

# It is gone from the live list...
az keyvault secret list --vault-name "$KV_NAME" --query "[].name" -o tsv | grep test-delete-me || echo "not in live list"

# ...but recoverable
az keyvault secret list-deleted --vault-name "$KV_NAME" \
  --query '[].{name:name, deleted:deletedDate, purgeable:scheduledPurgeDate}' -o table

az keyvault secret recover --vault-name "$KV_NAME" --name "test-delete-me"
az keyvault secret show --vault-name "$KV_NAME" --name "test-delete-me" --query name -o tsv

# Clean up for real
az keyvault secret delete --vault-name "$KV_NAME" --name "test-delete-me"
az keyvault secret purge  --vault-name "$KV_NAME" --name "test-delete-me"
```

**With `purge_protection_enabled = true` (prod) that last `purge` is
refused** — the secret cannot be permanently destroyed until the retention
window expires. That is the point: it defends against a malicious or
accidental hard delete, including by an administrator. The cost is that you
cannot reuse the vault name for up to 90 days, which is exactly why dev leaves
it off.

## 9. Interview answers this chapter gives you

**"How do you manage secrets?"**

> I start by trying to eliminate them. In this platform the database, the
> container registry, Key Vault itself, Service Bus and the CI/CD service
> connection all use managed identity or federated credentials, so there is no
> secret to manage at all — that is the strongest control available, because a
> secret that does not exist cannot leak or expire. What genuinely has to be a
> secret goes into Key Vault in RBAC mode, generated by Terraform so no human
> ever sees the value, with an expiry date set. It is delivered to pods by the
> Key Vault CSI driver as a mounted file rather than an environment variable —
> files stay out of etcd, are not visible in `kubectl describe` or
> `/proc/pid/environ`, and update in place when the secret rotates without a
> pod restart. I sync a secret into a Kubernetes Secret only when something
> truly needs an env var, and in our case that is exactly one value. Then
> there are two more layers: every secret read is audited to Log Analytics, so
> I can answer "who read what and when", and Gitleaks runs as a hard-fail gate
> on every PR and on full history on main so a secret never reaches the repo
> in the first place.

**"A developer accidentally committed an API key. What do you do?"**

> Rotate it first. The moment it hits a repository it is compromised —
> somebody may have cloned, CI may have logged it, a fork may exist — so
> revoking and reissuing the credential is step one, not step three. Then
> remove it from history properly with `git filter-repo` or BFG, force-push,
> and tell everyone to re-clone, because deleting the line in a new commit
> leaves it reachable by SHA forever. Then check the audit logs for use of
> that key between commit and rotation. And finally the process fix: why did
> the gate not catch it — was the pattern missing from the Gitleaks config, was
> the scan only on the diff and the key came in via a squashed merge, or did
> somebody bypass the branch policy. The reason our pipeline hard-fails on
> secret findings rather than warning is exactly this: a warning gets merged,
> and then you are rotating a production credential at 11 p.m.

**"Why not just use Kubernetes Secrets?"**

> They are base64, not encryption — anyone with read access to the Secret, or
> to an etcd backup, has the plaintext. You can enable encryption at rest for
> etcd, which helps, but you still have no rotation story, no audit trail of
> who read what, no expiry, and no central management across clusters. Key
> Vault gives all four: the value lives outside the cluster, every read is
> logged with the caller identity, secrets have versions and expiry dates, and
> the same vault serves every environment with RBAC scoped per identity. The
> CSI driver then delivers it as a file so it never has to enter etcd at all.
> I do still end up with one Kubernetes Secret, synced for a library that
> insists on an environment variable, and I treat that as a deliberate
> exception rather than the default.

**"What is the difference between Key Vault RBAC and access policies?"**

> Access policies are the legacy per-vault ACL model. Two problems with them:
> the granularity is the whole vault, so "read one secret" and "read every
> secret" are the same grant; and they are invisible to a normal RBAC audit —
> `az role assignment list` does not show them, so over-privileged access
> survives reviews. RBAC mode uses Azure role assignments, which means it
> scopes down to an individual secret, works with PIM and Deny assignments, and
> shows up in the same audit as everything else. The one thing people trip over
> in RBAC mode is that Contributor on the vault does not let you read a secret
> — the control plane and the data plane are separate, so a Contributor can
> delete the entire vault but cannot read one value out of it.
